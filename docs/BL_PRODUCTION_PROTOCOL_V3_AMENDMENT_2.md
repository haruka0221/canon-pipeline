# BL 本番 v3 プロトコル 改訂 2：BL が不正と判定したクエリの記録と続行

日付：2026-11-05
対象：`docs/BL_PRODUCTION_PROTOCOL_V3.md` §3（検索経路）・§7（安全装置）。凍結文書と `protocol_freeze_v1.json` は変更しない。

## 理由

2026-11-05 のバッチ 9 で、BL SRU が 1 クエリに対して診断 `200812 | Invalid query` を返し、凍結規則どおり夜が終了した（`BLP3_009_02413`、`alma.title == " by Louisa de"`、対象 `W000006940` / `OL16858741W`）。原因は Open Library 側の source 題名そのものが先頭空白つきの断片 `" by Louisa de"` であること。前処理の誤りではない。同じ対象の K1 クエリも同形で、同様に拒否される。対象一覧 `targets_v1.tsv` には前後空白つきの題名がもう 1 件（バッチ 22、`W000019221`）あるが、空白以外の理由で BL が拒否する題名も否定できない。

この診断は一過性でなく、再送しても結果は同じ。夜を止める意味がなく、放置すると同じ場所で毎回止まる。

## 変更

runner（`scripts/bl/run_bl_production_v3_v1.py`）に限り、**1 ページ目のリクエストに対して診断 `200812`（Invalid query）が返った場合**、その物理クエリの結果を `INVALID_QUERY_BL_REJECTED` として記録（request log に診断と raw を保存、status に同名の状態）し、次の物理クエリへ進む。再開時はこの状態を request log から復元し、再送しない。

`200812` 以外の診断、および 2 ページ目以降の診断は従来どおり `STOP_DIAGNOSTIC` で即終了する。

## 変わらないこと

- `build_plan`（クエリの作り方）、`"` を含むクエリの `SKIPPED_INVALID_QUERY` と q 経路の扱い。実行済みバッチと計画の作り方を揃えるため、題名の空白除去などの前処理は追加しない。
- `retries=0`、夜間窓、1 晩 7,000、累計 200,000、`STOP_HTTP`・`STOP_NETWORK`（改訂 1）・`STOP_PARSE` の扱い。
- BL への通知内容（拒否されたクエリを 1 回送る以外に送信量は変わらない）。

## 照合段階での扱い

`INVALID_QUERY_BL_REJECTED` は `SKIPPED_INVALID_QUERY` と同じく「その経路ではレコードなし」。対象 W の他経路（A1 など）が成立していれば、その経路の値だけで評価する。W 単位の `measurement_status` では、全経路が無効の場合に限り別状態として区別する（照合スクリプト v3 で定義）。

## 適用

2026-11-05 の再開から。実装 commit は本文書の次の commit。バッチ 9 の `BLP3_009_02413` は再開時に 1 回再送され、この規則で記録される。
