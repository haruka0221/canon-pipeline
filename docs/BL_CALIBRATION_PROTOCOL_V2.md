# BL 較正 v2 プロトコル（v2 calibration protocol）

作成 2026-10-18、凍結 2026-10-21。Claude Doc から書き出し。

## 1. 位置づけ

v2 は「v1 で失敗例を見た後に作った規則（R3）を、新しい標本で精度を測る」ための較正であり、本番の取得ではない。対象・経路・照合規則・保存先・安全装置をこの文書で先に凍結し、BL の返事（本番開始の可否、共有・公開の扱い）を待つ間はリクエストを 1 件も送らない。

v1 が残した問題は三つ。(1) 完全一致は古い初版レコードの約半分（13 件中 6 件）を落とす。(2) R3 は全 13 件を通すが、失敗例を見てから作った規則で精度が未測定。(3) 題名検索は上限なしで完了しても古い形のレコードを返さないことがあり、著者・キーワード検索だけで見つかる版がある（Kim、She の初版、Munchausen の 53 件中 39 件）。v2 はこの三つに答えを出す設計にする。

この下書きで「要確認」と書いた箇所は、`derived/bl_calibration/verification_pilot_v1/summary.md` と補遺を読んで確定する（§10）。本文は凍結前の草案で、リポジトリには `docs/BL_CALIBRATION_PROTOCOL_V2.md` として `bl-calibration-v2` ブランチに入れる想定。

## 2. 対象の凍結

対象は Project Works v7（`project_works_v7.tsv`、TSV sha256 `d82fd38c…cb760b5`）に固定する。v8 以降が出ても v2 は動かさない。`registry_v4` は v5 由来なので使わず、BL 用の対象一覧を v7 と `work_identity_map_v7` から作り直す（§3）。

| 区分 | 件数 | v2 での扱い | 結果の値 |
| --- | --- | --- | --- |
| 有効 W（source-light を除く） | 32,065 | 較正標本の母集団 | 件数または 0 |
| source-light W（Alcott `W000014515`） | 1 | OL の題名・著者がないため検索対象外 | NA（`NOT_RETRIEVED_SOURCE_LIGHT`） |
| 同定保留 `identity_suspended` | 16 | 計測しない（旧 OL Work の題名で検索しない） | NA（`NOT_MEASURED_IDENTITY_SUSPENDED`） |
| 置き換え済み superseded | 7 | 対象外 | 行を持たない |
| 未解決ユニット | 761 ユニット / 2,083 OL target | 別レーン `target_lane = unresolved_source`、`project_work_id = NULL` | ユニット単位の件数、W へは合算しない |

理由を三つ書いておく。有効 W の数は 32,066 だが、Alcott は OL source Work の SAME メンバーを持たないので BL の題名検索を組めない。OpenAlex 側と同じく 0 ではなく NA にする。同定保留 16 は旧 OL Work の題名で検索すると過剰統合された候補が戻るので、v6 の隔離と同じ理由で計測しない。未解決ユニットは OpenAlex と同じ診断レーンに置き、W の値には入れない。

確定（2026-10-21、`target_frame_v1`）：未解決 OL 別名 2,083、同定保留 OL 別名 17、有効 W 32,066 のうち複数別名を持つ W 550。ユニット数 761 は本流の値で、BL v2 ではユニットへの束ねは行わず OL 別名単位で扱う。数え直しの出典は `work_identity_map_v7` で数え直す。

## 3. 較正標本の設計

v2 は全 32,065 W ではなく標本で行う。BL は大規模抽出を認めておらず、数千件までの条件付き抽出を提案しているので、較正の総リクエスト数をその範囲に収め、本番の規模は BL の返事を受けてから別に決める。

標本は三つの層に分け、v7 と講習会の OL 索引（`ol_index_full_v1.sqlite` の `edition_counts.n`、旧 `ol_edition_counts.tsv` と 34,789 件で一致確認済み）から引く。層はリクエストを送る前に凍結する。

| 層 | 目的 | 抽出 | 件数（案） |
| --- | --- | --- | --- |
| S1 無作為 | 母集団全体での網羅率・精度の推定 | 有効 32,065 W から単純無作為 | 150 W |
| S2 版数で層化 | 版の多い作品と少ない作品で挙動が違うか | `edition_counts.n` を 1、2–5、6–20、21+ の 4 区分、各区分から無作為 | 各 25 W = 100 W |
| S3 v1 再検証 | v1 の 21 対象（19 W＋未解決 2 ユニット、`bl_verification_pilot_v1_sample.tsv`）を新しい経路・規則で再測定 | v1 の対象をそのまま | 21 対象 |

S3 は v1 の失敗例を見てから作った R3 の「学習データ」にあたるので、精度の推定（§5）には入れず、再現性の確認だけに使う。精度と網羅率の推定は S1 と S2 だけで行う。

版数は層を切る変数としてだけ使う。版数ゼロや Wikidata の有無を対象に入れる・外す基準にはしない（source の有無を scope の基準にしないという原則）。複数の OL Work が一つの W に束ねられている場合（Heart of Darkness の 4 W はそれぞれ別）、W の全 OL 別名から検索語を作り、どの別名で見つかったかを記録する。

網羅率の物差しは v1 と同じく「独立に確かめた英国初版」とする。S1・S2 から 30 W 程度を選び、BL 以外の典拠（ODNB、作家別書誌、初版目録）で英国初版の年・出版社を先に表に書いてから、BL の結果を見る。

凍結済み（`ecf1a4d`、種 20261021、`sample_targets_v1.tsv`）：S1 150 / S2 100 / S3 20、計 270 対象、別名 278 件。v1 の 21 対象のうち 1 件は無作為で S1 に入ったので S3 は 20。母集団 32,065 W の版数の分布は、1 版 13,832、2–5 版 10,199、6–20 版 4,920、21 版以上 3,111、版数なし 3（target 補正分）。標本の別名はすべて `USE_ORDINAL0` で、著者語の無い対象（母集団の約 1%）は入っていない。著者語なしでの K1・A1 の挙動は v2 では測れない。v1 の 21 対象のうち Q2 の初版表は 12 行（11 行が判定可能、Heart of Darkness は上限で判定不能）、Q3 の 5 対象は全部 `title_route_hit`。v1 は 21 対象で 2,605 レコードだったので、266 W では約 3 万レコードになり、§5 の人間判定 500 件を抜くには足りる。

## 4. 検索経路

v2 は T3 をやめ、T2・K1・A1 の三経路を全対象で一律に走らせる。経路ごとに「取れた・取れなかった」を記録し、どの経路が初版・古い形のレコードを拾うかを測る。v1 で題名検索の上限なし完了でも古いレコードが返らなかった事実（Kim、She）があるので、T2 単独の結果を網羅率とは呼ばない。

| 経路 | CQL（v1 プロトコルどおり） | 上限との関係 | v2 での役割 |
| --- | --- | --- | --- |
| T2 title_exact | `alma.title == "<title>"` | 200 件（方針上の上限）で `CAPPED` | 主経路。打ち切り有無を必ず記録 |
| K1 keyword | `alma.all_for_ui all "<title> <author surname>"` | 同上 | 古い形のレコードの補完。Kim・She の初版、Munchausen の 39/53 はここだけで取れた |
| A1 author_only | `alma.creator all "<author>"` | 先に件数だけ取り、200 以下のときだけ全件取得（`SKIPPED_POLICY_CAP`） | 上限未満の作家だけ。v1 では 16 著者中 3 だけ完了 |
| T1 title_exact_author | `alma.title == "<title>" and alma.creator all "<author>"` | — | 廃止候補。T2 の部分集合なので v2 では送らず、T2 の結果に著者一致を後から掛ける（§5） |
| T3 title_phrase | `alma.title = "<title>"` | 短い題名で `CAPPED`（Kim・She）、廃止 |

v1 の取得は `maximumRecords=20` で `startRecord` を進めるページ送りなので、1 つの論理クエリが複数の HTTP リクエストになる（96 物理クエリで 296 リクエスト）。§7 の予算はリクエスト単位で数える。上限の扱いは三段階にする。(1) 返却が 200 件未満なら完了。(2) 200 件ちょうどなら「打ち切り」と記録し、v2 では続きを取りに行かない（ページ送りの追加リクエストは本番の設計に回す）。(3) 打ち切られた検索の結果は網羅率の分母から外さず、「打ち切りで見つからなかった可能性」として別に数える。

検索語は W の全 OL 別名から作る。同一 W の複数別名で同じ正規化後の検索語になれば 1 回にまとめ、どの別名からの検索語かは残す（OpenAlex の logical query / physical execution の分離と同じ）。著者語は `openlibrary-query-author-selection-v1` の ordinal-0 選択を使い、`NO_OL_AUTHOR` の 361 件は T2 だけになることを記録する。

要確認：T1 と T2 の違い、T3 の定義と廃止理由、K1 の語の組み方、A1 の上限判定の方法（著者レコード総数を先に 1 回問い合わせるか）。

## 5. 照合の規則と精度の測定

照合規則は R3（角括弧除去後の前方一致、語の切れ目付き）に著者一致を加えた「R3＋著者」を本命とし、完全一致（v1 の G3 相当）と R3 単独を比較対象として同じレコードに並べて適用する。規則はリクエストの前に凍結し、結果を見てから変えない。

精度の測り方：

1. S1・S2 の全返却レコードに三つの規則を機械的に適用し、各レコードに `exact` / `r3` / `r3_author` の三つの真偽を付ける。
2. `r3_author` が真のレコードから無作為に 300 件、`r3` 真かつ `r3_author` 偽から 100 件、`r3` 偽から 100 件を抜き、人間が盲検で「対象作品の版か」を判定する。判定者には規則の結果を見せない。
3. 人間判定を先に表にして凍結し、その後で規則との一致を集計する。層化した point estimate と、v1 と同じく設計ベースの近似 95% 信頼区間を出す。
4. LLM を使う場合は人間判定の前に指示文をコミットし、モデル名を記録し、出力を直さない。LLM は人間の代わりではなく、人間が見る候補の並べ替えにだけ使う。

照合の後に、§9a の三つの要件を別の層として扱う。

- 重複除去：BL の返却レコード数と刊本の数は別物（v1 でも Tess 2 件、She 3 件の重複レコード）。同一刊本とみなす鍵（著者・題名の正規化形・出版者・出版年・ページ数）を凍結前に決め、`records` と `publications` を別の表にする。公開する件数は両方を並べ、どちらかを「版の数」と呼ばない。
- 関係判定の二軸：人間判定は「対象作品か」だけでなく「刊本の関係」も付ける。区分は v1 プロトコル §7 の語彙をそのまま使う：`target_alone` / `target_with_other_works` / `target_in_collection` / `other_language_version` / `unrelated` / `ambiguous` / `other`（`other_flag` 付き）。精度の推定は「対象作品か」で行い、関係の分布は別に報告する。
- 複数 W への帰属：同じ BL レコードが複数の W の検索から返った場合（Heart of Darkness の 4 W）、無条件に全部へ帰属させない。W ごとに照合規則を適用し、複数 W で真になったレコードは `multi_w_candidate` として分け、人間判定の対象に含める。v2 では帰属規則を決めず、何件がこの状態になるかを数える。

網羅率は §3 の英国初版表（先に凍結）に対し、どの経路・どの規則で見つかったかを作品ごとに記録する。v1 の G1（11 作品中 10）に相当する値を S1・S2 の初版表で再計算し、v1 の値と並べて書く。

著者一致の定義は決めておく必要がある。候補は、姓の完全一致、または姓＋名の頭文字一致。BL の MARC 100 フィールドの形（Smith, John, 1870-1930）に合わせて正規化し、生没年は照合に使わない。これは要確認ではなく決定事項として §9 に書く。

## 6. データの置き場所と公開範囲

BL のレコードの中身は、取得した瞬間から非公開の場所にだけ書く。v1 で後から 7 ファイルを公開ツリーから外した手順（`f125b90`）を v2 で繰り返さない。実行スクリプトの保存先は固定で、公開リポジトリのパスを指せないようにする。

| 場所 | 中身 | 公開 |
| --- | --- | --- |
| `サーバー /media/hdd1/user/tsutsui/bl/calibration_v2_raw/（chmod 700）、控えは PC ~/bl_raw/calibration_v2/` | SRU の生応答（XML）、解析済みレコード TSV、照合候補、人間判定の入力表 | 非公開。sha256 を `SHA256SUMS` に記録 |
| `derived/bl_calibration/calibration_v2/`（公開リポジトリ） | manifest.json、集計結果、精度・網羅率の表、レコード識別番号（marc_001 / MMS ID）だけの一覧、研究の記述中の短い引用 | BL の返事で「識別番号・短い引用の公開可」が確認できるまで、識別番号の一覧も公開ツリーに入れない |
| `docs/BL_CALIBRATION_PROTOCOL_V2.md` | この文書 | 公開 |
| `scripts/bl/` | 実行・解析スクリプト | 公開。認証情報は環境変数から読み、値をどこにも書かない |

公開ツリーに入れる前の確認を手順にする。`git status --short` の一覧を見て、`derived/bl_calibration/calibration_v2/` 以下に生レコードの列（題名、出版社、出版地、著者の文字列）を含むファイルがないことを、列名の grep で確かめてから名指しで add する。manifest には生データの sha256 と行数だけを書き、生データのパスは非公開側のパスを記す。

BL への問い合わせ 2（非公開の場所だけに保存）と 3（集計・短い引用・識別番号の公開）の返事によって、上の表の「公開」列は変わる。返事が来たらこの表を更新し、変更前の版を履歴に残す。

## 7. 安全装置とリクエスト予算

v1 の実績は 21 作品で 296 回（約 14 回/作品）なので、§3 の 266 W では約 3,700 回と見込む。3 秒間隔なら約 3 時間で、英国の夜間 2 晩で終わる。累計上限は 4,000 回とし、超えたら止める。BL には本番と同じく「約 3,700 回、上限 4,000、2 晩」と事前に知らせ、了承を得てから実行する。

見積もりが外れた場合の規則を先に決めておく。S1 から無作為に選んだ最初の 30 W を先に処理し、その時点の 1 W あたり実測回数 × 266 が 4,000 を超えるなら停止し、S2 の各区分を 25 → 15（計 60 W）に減らして再開する。S1 と S3 は減らさない。この判断に使う数字は「30 W の実測回数」だけで、結果の中身は見ない。

安全装置は実行スクリプトに組み込み、設定ファイルではなくコードで固定する：

- 英国夜間判定：`zoneinfo.ZoneInfo("Europe/London")` で現地時刻を取り、22:00–06:00 の外では送信しない（BL に伝えた時間帯に合わせる）。10 月 25 日に BST が終わるので JST からの換算は固定しない。
- 間隔：前のリクエストの応答受信から 3 秒以上待つ（送信間隔ではなく応答後の待ち）。
- 停止条件：HTTP 429、5xx、接続エラー、SRU の diagnostic 応答のいずれかで即停止し、自動再試行しない。再開は人が判断する。
- 全体上限：累計 4,000 回（再開した晩を含めて数える）。1 晩の上限は 2,500 回。
- 逐次実行：並列なし、1 セッションだけ。
- ログ：1 リクエストごとに時刻（UTC と London）、経路、検索語、HTTP 状態、返却件数、打ち切り有無を非公開側に追記する。再開時はログから完了済みを読み、同じ検索語を二度送らない。

実装済み：scripts/bl/run_bl_calibration_v2_v1.py（v1 の送信・解析を流用、リトライなし、--phase early → 人の確認 → --phase rest --early-check-ack）と scripts/bl/mock_sru_server_v1.py。2026-10-21 に模擬サーバーで 5 項目を確認済み：夜間外で 0 件送信、429 で即停止、上限で停止、再開で完了ページを送り直さない、raw がリポジトリに書かれない。計画は 810 論理 / 784 物理 / 先行 90（4e3fe24）。本番の実行はサーバーで tmux の中で行う（PC は閉じられる）。raw はサーバーの /media/hdd1/user/tsutsui/bl/calibration_v2_raw/（chmod 700）、ログと計画はサーバーの BL 用 clone からコミットして push する。v1 との差は「3 秒」と「エラーで自動停止」と「上限」の三つで、2 秒・手動停止の v1 の運用より保守的にする。

## 8. 成果物と manifest

ファイルは「リクエスト前に凍結するもの」と「取得後に作るもの」を分け、前者は取得前にコミットする。スクリプトは出力より先にコミットする（§8 のルール）。

| 時点 | ファイル | 置き場所 | 中身 |
| --- | --- | --- | --- |
| 凍結前 | `calibration_v2_targets.tsv` | 公開 | W ID、`target_lane`、層（S1/S2/S3）、OL 別名、検索語、著者語、v7 の `measurement_status` |
| 凍結前 | `calibration_v2_first_editions.tsv` | 公開 | 約 30 W の英国初版（年・出版社・典拠）。BL の結果を見る前に凍結 |
| 凍結前 | `calibration_v2_matching_rules.md` | 公開 | exact / r3 / r3_author の定義と正規化手順 |

| 取得後 | `requests_log.tsv` | 非公開 | §7 のログ |
| 取得後 | `records_raw/` と `records_parsed.tsv` | 非公開 | SRU 応答と解析済みレコード |
| 取得後 | `matching_results.tsv` | 非公開 | レコード × 規則の真偽、著者一致の根拠 |

| 取得後 | `calibration_v2_summary.json` と `summary.md` | 公開 | 経路別件数、打ち切り数、精度・網羅率と信頼区間、短い引用 |
| 取得後 | `calibration_v2_manifest.json` | 公開 | 非公開ファイルの sha256・行数・パス、総リクエスト数、実行日時、停止の有無 |

manifest に必ず入れる来歴：対象の同定の版（v7 と sha256）、OL 索引の版（`ol_index_full_v1.sqlite`）、検索経路と規則の版、スクリプトのコミット、総リクエスト数と実施した晩の日付、BL の返事の日付と内容の要約（返事の原文は入れない）。

公開側の数字は「BL の SRU で、この経路と規則で、この日に返ったレコード」の件数であり、BL の所蔵の全体でも、その作品の英国刊行の総数でもない。summary.md の冒頭にそう書く。

以下は BL の結果を見る前に決め、`calibration_v2_protocol_freeze.json` のコミットで固定する。気づいたことは結果を見る前に補遺に書く。
