## 3. Decision semantics

### MATCH

A Goodreads work identity has been accepted by the current resolution
pipeline.

Only `MATCH` rows populate the accepted field:

```text
goodreads_work_id
```

### NO_MATCH

A candidate identity was explicitly evaluated and rejected.

This is an identity decision. It is not a claim that Goodreads contains no
record corresponding to the Open Library source record.

### NO_CANDIDATE

The current candidate-generation and resolution pipeline did not produce a
candidate that could be accepted.

This must not be interpreted as confirmed absence from Goodreads.

### AMBIGUOUS

Identity remains unresolved.

No Goodreads identity has been accepted.

## 4. Accepted identity versus candidate evidence

Accepted Goodreads identity and candidate evidence must remain separate.

In `goodreads_work_crosswalk_v1`:

```text
goodreads_work_id
```

means an accepted Goodreads identity and is populated only for `MATCH`.

Fields beginning with:

```text
candidate_
```

preserve candidate evidence and do not by themselves represent an accepted
identity.

This distinction must be retained in future releases.

## 8. Future LLM-assisted review

LLM-assisted review of the 909-row singleton-FULL queue has not yet been run.

The 909 rows are intentionally retained so that this work can be resumed
later.

The future task is not merely title matching. It is an identity-resolution
task.

For each candidate, the reviewer should consider evidence such as:

```text
Open Library:
- title
- author name / author identifiers
- publication-year evidence

Goodreads candidate:
- candidate work ID
- candidate title / original title
- publication-year evidence
- contributors and contributor roles

Cross-source identity evidence when available:
- corrected OL -> Wikidata work crosswalk
- Wikidata P50 authorship evidence
- person QIDs and aliases
- translator / editor / other contributor roles
```

The expected identity decision space should remain compatible with:

```text
MATCH
NO_MATCH
AMBIGUOUS
```

An LLM decision must preserve its evidence and rationale.

Temporal triage must be supplied as contextual evidence, not as a hard rule.

## 9. LLM protocol not yet frozen

The following have not yet been finalized for the 909-row review:

```text
model/provider
prompt version
structured output schema
confidence policy
benchmark sample
human adjudication protocol
batching strategy
final output filenames
```

Do not begin a full 909-row production run before these are explicitly
versioned.

A future resumption should first create and adjudicate a small representative
benchmark drawn from the 909 rows, including cases from all four temporal
triage categories.

Only after evaluating the proposed LLM-resolution procedure should the full
queue be processed.

## 10. Versioning rule for future resolution

Do not overwrite:

```text
goodreads_work_crosswalk_v1
```

or the v13 residual files.

Future LLM-assisted decisions should first be stored as a separate,
versioned evidence/assertion layer.

After validation, a new crosswalk release should be generated, for example:

```text
goodreads_work_crosswalk_v2
```

The exact filenames and schema for the future LLM layer are not yet frozen and
must be defined before the first production run.

## 11. Resume checklist

When returning to the 909-row LLM review:

1. Check out the intended project branch and confirm the baseline commit.
2. Rebuild `goodreads_work_crosswalk_v1`.
3. Rebuild the local DuckDB query layer.
4. Verify that the unresolved singleton-FULL queue still contains 909 rows.
5. Verify the four temporal-triage counts.
6. Confirm that accepted IDs remain empty for all 909 unresolved rows.
7. Freeze the LLM review protocol: model, prompt, schema, benchmark, and
   provenance.
8. Construct and manually adjudicate a representative benchmark.
9. Evaluate the LLM procedure before full-batch processing.
10. Preserve raw outputs and normalized decisions separately.
11. Do not overwrite v1.
12. Generate a later crosswalk version only after review and validation.

## 13. Relationship to project-level identity

Goodreads Work IDs remain source identifiers.

They are not the project-level conceptual `work_id`.

The project-level identity layer remains separate and will later connect
Open Library, Goodreads, Wikidata, and other source entities without replacing
their original identifiers or source evidence.
